# Architecture and engineering boundaries

The plain browser shell owns user intent and presentation. `SceneDocument` owns durable scene state. `Viewport` projects that state into Three.js objects and evaluates animation without rewriting stored base transforms. `ProjectClient` owns acknowledged server snapshots and revision coordination. The same API handler source is compiled for hosted Workers and the local Node launcher.

The scene uses stable IDs rather than Three.js UUIDs. This permits validation, history, file exchange, and collaboration without serializing renderer internals. Renderer resources can be recreated from document data. PBR materials are shared by scene material ID. Cloners use one InstancedMesh rather than independent draw calls per clone. Geometry descriptions and object references avoid rebuilding unaffected meshes; rendering is requested on changes and camera movement, or continuously during playback.

A transaction clones document state for undo. This is predictable and useful at modest scale, but is not a compact command-log implementation. Large meshes can consume significant memory across the bounded 80-entry history. CPU serialization, validation, and full-scene polls are additional scaling limits. No benchmark establishes maximum professional scene size or sustained FPS on physical GPUs.

Project persistence uses a serialized scene per database row with a monotonically increasing revision. Client diffs are object/material records or specific scene metadata. The server applies a complete batch, validates the resulting graph, and conditionally updates the prior revision. This prevents silent replacement on concurrent writes. Polling merges disjoint records, but refuses overlap or an invalid combined graph. There is no CRDT or distributed operation log.

Hosted authentication depends on trusted dispatcher headers. Authorization is checked on every project endpoint. Project owners alone manage members and deletion; editors can modify scenes; viewers can read and review. Project access does not widen the site's audience. The local launcher intentionally supplies a fixed identity and is not an enterprise server.

The static application includes the necessary Three.js source modules and local addon imports so it does not depend on a runtime public CDN. Required shader code is generated by Three.js. Astrum is not an independent low-level GPU driver implementation, nor an equivalent of Redshift.
